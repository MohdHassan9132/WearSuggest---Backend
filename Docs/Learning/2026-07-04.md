# Session - July 4, 2026

## Subscription Redesign

Today I finished a full redesign of the Subscription feature.

The main goal was not just to make payments work. I wanted the subscription system to become easier to understand, easier to extend, and much easier to maintain later.

This session ended up being more about responsibilities than about payment integration.

## What I Built

I implemented a subscription system that supports both `Users` and `Sellers`.

The final design uses two different collections:

- `Subscription`
- `SubscriptionOrder`

That separation became the most important design decision of the session.

`Subscription` now represents only the current active state.

It answers questions like:

- What plan is active right now?
- How many credits are available right now?
- When does the subscription expire?

`SubscriptionOrder` now represents payment history.

It stores every purchase attempt and keeps that history even after the active state changes.

That means I no longer need to overload one collection with two responsibilities.

## The Biggest Change In My Thinking

At first, I was still thinking in a way that mixed "what is active now" with "what happened in the past."

I almost made `Subscription` depend too much on `SubscriptionOrder`.

I also considered storing plan information only inside orders and then deriving everything from there.

The problem is that history and active state are not the same thing.

An order tells me:

- what someone tried to buy
- what payment happened
- whether it succeeded or failed

A subscription tells me:

- what is active now
- how many credits are left now
- when the current period ends

Once I accepted that these are different responsibilities, the rest of the design became much cleaner.

## Repositories Became Much Simpler

One of my earlier mistakes was letting repositories know too much.

I had repository methods doing more than database work. They were helping decide what a subscription object should look like.

That was a bad direction.

During this session I pushed object construction back into the service layer.

Now the repositories are much more boring, and that is a good thing.

They now receive already-prepared objects like:

```js
{
  subscriber,
  subscription
}
```

or:

```js
{
  subscriber,
  subscription,
  order
}
```

Then they simply spread those objects into Mongo.

This matches something my mentor keeps pointing out in different ways:

> Repositories should stay dumb.

That lesson really clicked for me today.

## The Service Now Builds Domain Objects

Instead of asking repositories to shape data, the service now does the real business work.

That includes:

- validating plan selection through configuration
- resolving whether the subscriber is a `userId` or `sellerId`
- building the active subscription object
- building the subscription order object
- converting Razorpay's order response into my own order fields

The service now reads much closer to the actual business flow.

That feels much better than hiding business decisions inside persistence code.

## Builder Functions Helped More Than I Expected

I introduced small builder methods:

- `buildSubscription()`
- `buildSubscriptionOrder()`
- `razorpayOrderToSubscriptionOrder()`

At first this looked like a small cleanup.

But after doing it, I realized it solved several problems at once:

- less duplicated object construction
- clearer naming
- easier refactoring
- easier documentation

Each function now explains what kind of object is being built and from what source.

That made the service easier to read line by line.

## Plan Configuration Finally Became The Source Of Truth

Earlier I was repeatedly reaching into:

```js
SUBSCRIPTION_PLANS[role][plan]
```

all over the code.

That worked, but it made the service noisy and repetitive.

This session improved that by using:

```js
getPlanConfig({ role, plan })
```

Now everything downstream receives one normalized object:

```js
{
  name,
  amount,
  credits,
  currency
}
```

This was a small API improvement inside my own code, but it made the whole feature feel more consistent.

It also reinforced another important lesson:

> If many parts of the system need the same business data, it should come from one source of truth.

## Subscriber Resolution Needed Its Own Place

I was repeating subscriber mapping logic too many times.

In several places I was deciding:

- if role is `USER`, store `userId`
- if role is `SELLER`, store `sellerId`

That repetition was unnecessary.

I moved it into:

```js
resolveSubscriber({ role, subscriberId })
```

Now the mapping and role validation happen in one place.

This is another example of a small helper removing a lot of repeated reasoning from the rest of the code.

## Validation Became More Consistent

I was also manually checking and normalizing strings in more than one place.

That was starting to become repetitive and fragile.

Using `stringValidator()` helped centralize that pattern:

- validate the type
- trim whitespace
- reject empty values

Then the code can safely normalize with things like:

```js
stringValidator(value).toUpperCase()
```

instead of rewriting the same validation logic again and again.

This is one of those changes that feels small in the moment but prevents a lot of sloppy duplication later.

## Free Plans Forced Me To Clarify The Rules

Users and sellers both have a `FREE` plan in configuration, but `FREE` is not meant to go through Razorpay.

So I added an explicit rule:

- free subscriptions can be initialized internally
- free subscriptions cannot be purchased through the create-order endpoint

That means purchase requests for `FREE` are rejected before Razorpay is even called.

I like this because it protects the payment flow from unnecessary edge cases.

## Credits Reset On New Subscription

I spent time thinking about whether credits should carry forward.

For example:

- FREE gives 100 credits
- user has 20 left
- user buys PRO

Should the result be `520` or `500`?

I decided the answer should be `500`.

Credits now reset based on the newly activated plan instead of being accumulated.

This keeps the active subscription state simpler and avoids hidden rollover behavior.

I think that was the right tradeoff for now.

## Expiration Became Simpler Too

The final rule is:

- `FREE` subscriptions do not expire
- paid subscriptions get `activatedAt`
- paid subscriptions get `expiresAt`
- expiry is currently `30 days`

That rule is easy to explain and easy to store.

It also keeps `Subscription` focused on the current state instead of historical transitions.

## Current Plan Belongs On Subscription

I almost treated the order record as the only place that needed plan information.

But that would have made active-state reads unnecessarily indirect.

`Subscription` should not need to "look back into history" just to answer:

- what plan is active right now?

So the final design keeps `currentPlan` directly on `Subscription`.

That is duplicated from a pure history perspective, but not from an active-state perspective.

It belongs there because `Subscription` is the current truth.

## Webhook Flow Feels Better Now

The activation flow is much clearer now:

```text
Webhook
  |
  v
Find SubscriptionOrder
  |
  v
Verify webhook signature
  |
  v
Mark order as success
  |
  v
Build Subscription object
  |
  v
Activate Subscription
```

The order remains history.

The subscription becomes the active state.

That is exactly the separation I wanted.

## Mistakes I Want To Remember

The main mistakes from this session were not syntax mistakes. They were design mistakes:

- I mixed business logic into repositories.
- I let repositories shape objects that should have been built in the service.
- I repeated subscriber mapping.
- I almost duplicated plan access everywhere.
- I manually normalized strings in multiple places.
- I almost made `Subscription` too dependent on `SubscriptionOrder`.
- I briefly thought one collection might be enough for both active state and history.

Each of those mistakes pushed me toward the final design.

That is probably the biggest lesson from today: the final structure became clearer only after I noticed which responsibilities were being mixed together.

## What Helped Most

A few ideas made the final implementation much stronger:

- keep repositories dumb
- let services build domain objects
- keep one source of truth for plan configuration
- separate payment history from active subscription
- use tiny helpers for repeated logic
- choose names that explain intent clearly

None of these are flashy improvements, but together they made the feature feel much more professional.

## Future Notes For Myself

- The subscription flow is now structurally cleaner, so future work should try to preserve that separation.
- If more payment providers are added later, the current builder pattern should make that easier.
- If expiration rules become more complex, `buildSubscription()` is the right place to evolve that logic.
- If order states expand later, `SubscriptionOrder` is already the correct place for that history.
- I should keep watching for places where helpers can remove repeated mapping or normalization logic before duplication spreads again.

This session was a good reminder that maintainability usually comes from clear boundaries, not from clever code.
